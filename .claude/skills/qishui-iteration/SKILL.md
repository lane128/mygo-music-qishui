# 汽水插件迭代

将本次任务推进到用户已授权的交付位置。先理解目标，按实际影响选择必要检查；不重复测试，不增加无关步骤。加载本 skill 不授予提交、推送、发布、删除或真实账号写入权限，也不替代工具权限设置。

本文件路径为 `.claude/skills/qishui-iteration/SKILL.md`。以下路径以项目根目录为基准；先从当前目录定位仓库根目录，不能假设 shell 已在根目录。发布规则和验证矩阵以 [RELEASE.md](../../../RELEASE.md) 为唯一说明入口；如本 skill 与其冲突，先核对用户当前授权及项目指引，不自行放宽限制。

## 1. 识别任务与授权

结合本次任务上下文识别授权，不要求用户必须使用特定关键词。组合请求取所授权步骤的并集，明确的“不提交 / 不推送 / 不发布 / 不改版本”优先。

| 任务 | 执行范围与停止位置 |
| --- | --- |
| 查看、分析、review | 只读调查、验证与报告，不修改项目文件 |
| 先设计、先出草稿 | 产出设计或预览，不安装规则、不提交发布 |
| 修复、实现 | 调查、必要修改与相关回归，交付实现结果 |
| 打自测包 | 在实现授权内构建本地包，默认不改版本、不自动安装 |
| 准备指定版本 | 同步版本、必要说明，形成并检查候选，不提交或创建远端 Release |
| 提交 | 仅提交授权文件，不自动推送 |
| 提交推送 | 提交并推送授权文件，不创建新 Release |
| 提交推送并发布 | 完成所授权改动、候选、提交、标签、Release 及公开核验 |
| 发布已有提交 / 已准备版本 | 核对提交和候选，按授权推送必要标签并发布，不额外提交工作区改动 |
| 更新发布说明 | 只修改指定 Release 正文，不替换附件、不移动标签 |
| 更新介绍 / Topics | 只修改用户指定的仓库元数据字段 |
| 清理旧产物 | 先盘点依赖，再删除明确授权的旧生成产物 |

已明确授权的同一步骤不重复询问；已完成任务的授权不自动延续到新的独立任务。只有无法从用户请求、代码、文档或惯例解决，且会改变授权范围或破坏性影响的决定才询问。需要确认时，先完成不依赖该决定的调查和可审阅准备，再一次说明具体缺少哪项授权。

调用示例：

```text
/qishui-iteration 修复歌手页，打个自测包，先不提交
/qishui-iteration 准备 1.0.12
/qishui-iteration 提交推送当前修复
/qishui-iteration 发布已准备的 1.0.12
/qishui-iteration 更新发布说明
/qishui-iteration 清理 dist 旧产物
```

## 2. 确认范围并实现

1. 读取项目指引及 `RELEASE.md`，检查工作区、分支、Git remote 和用户已有改动。简短说明本次修改、影响及验证范围。
2. 发布任务先只读核对 GitHub 最近正式 Release 对应的 tag、提交及其与当前分支的关系。按 `RELEASE.md` 的基线规则将明确的 `--base` 传给入口；不能仅看最近提交或本地最近 tag。
3. 仓库地址从 remote 核对；宿主路径、最低版本、工具链与原生资产从 manifest、配置及当前环境发现，不写死个人目录、随机 dist 目录或临时路径。缺少外部配置且无法发现时才询问。
4. 先取得复现或原因证据，再做可验证的小步修改。只实现用户要求与必要配套；额外可见功能、设置或开关先征得同意。
5. 只修改插件；宿主验证优先使用现有 overlay，不覆盖宿主生产代码。保留用户未提交工作，不使用 reset / clean 清理工作区。
6. 需要编辑或提交时默认使用任务分支；只读任务不为此改分支。重要变更条件允许时独立审查，最多三轮，后续聚焦新修改；并行 Agent 各用独立 worktree，不擅自引入多 Agent 编排。
7. 凭据、二维码令牌、账号标识、签名材料和原始上游错误不得出现在聊天、日志、仓库、提交或发布内容中。不读取或复制官方 App 保存的账号凭据，不绕过试听、会员或地区授权。
8. 真实账号写入仅按明确授权验收，不自动执行关注、收藏、排序或评论写入；自动化回归使用模拟服务。传递凭据使用既有私有通道。

## 3. 选择验证并复用结果

根据 `RELEASE.md` 的矩阵取本次影响范围的并集，不另维护一份矩阵。

- 开发期优先定向测试；功能收敛后执行一次必要的源码全量。纯文档只检查内容、引用、链接和差异，不跑运行时全量、不打包。
- 登录 / 会话 / 写入关注失效、取消、换号、迟到结果、身份核对及不重复写入；原生 / 隔离 / 音频按矩阵增加回归、对应模块 race 和平台检查。
- 宿主 API、最低版本或布局变化时检查当前与最低版本宿主；不默认跑宿主全仓，也不启动完整宿主反复截图。
- 真实音频按影响验证格式、时序、回退、seek、缓存与下载；自动化结果、设备执行和人工试听分开记录。未改相关输入时不重复真实歌曲抽样。
- 复用必须能核对源码与测试输入、宿主、工具链、固定资产、执行条件及对应日志。只记录 HEAD 不够；报告存在但证据已删除或输入无法确认时，不能声称结果已验证。
- 版本或文档变化可复用无关源码回归；新的 ZIP 仍须做版本、包一致性和安装检查。包内执行输入不变的检查按现有指纹机制复用。
- 检查失败先定位，不靠重跑取得一次通过；两次失败补日志等证据，三次失败整理已尝试方案并重新分析。必要自动化失败停止依赖该结果的后续步骤。
- 缺设备或人工验收时保留 pending；用户已明确授权在同一范围先发布收集反馈的，按 `RELEASE.md` 记录限制，不反复索取确认、不改记为通过。

## 4. 形成可追踪的候选

复用 `package.json` 和 `scripts/release.mjs` 已有入口，先按任务选择所需命令，不要求每次顺序重跑全部阶段：

```sh
npm run release -- plan
npm run release -- check --output <candidate>
npm run release -- prepare --version <X.Y.Z> --base <published-tag> \
  --host-source <current-host> --host-source <minimum-host> \
  --output <candidate>
```

上面是参数示意，执行前替换为已核对的实际值。宿主数量按变更范围选择；自测默认保持版本并复用已有打包入口，不为每次任务创建新的工作流脚本。`prepare` 始终只做本地准备，不能因命令成功自动取得发布授权。

- 版本策略、三份版本同步及四平台规则按 `RELEASE.md` 执行。原生组件复用固定哈希已通过的输入，每个平台构建一次；不以旧 ZIP 代替新源码构建。
- 每个候选集中保存在一个目录，维护一份 `report.json`，记录输入标识、通过 / 失败 / 跳过、复用来源、日志、包大小 / SHA-256 和未完成项。不要逐阶段新建手写报告。
- 发布授权与事实另记 `publication.json`。现有入口可能因人工待验收令 `readyForRelease` 为 false；保留原结论，不把 false、skip、pending 改成通过，不为此重写发布入口。
- 修改实现或构建输入后，按依赖关系重跑受影响步骤；仅 Git 元数据或文件清单变化导致的指纹差异也必须有可核实解释，不能忽略差异或伪造匹配。
- [README.md](../../../README.md) 与 [README.en.md](../../../README.en.md) 维护用户介绍，相关功能、安装包及最低版本同步。其他说明按 `RELEASE.md` 的职责更新；[VALIDATION.md](../../../VALIDATION.md) 仅收尾补必要结论，不追加逐步流水账。

## 5. 按授权提交与 GitHub 发布

先完成候选与必要检查，再执行已授权的外部操作。GitHub 的 tag / Release / draft / Latest 机制与本项目的版本同步、附件命名约定分别说明，不把项目惯例宣称为 GitHub 统一要求。

1. 只暂存授权文件，检查实际提交差异。使用仓库配置的作者信息，提交说明包含改动、实际验证和回滚方式；不自动提交与本次无关的工作。
2. 按用户授权处理推送与合并，不强制引入 PR。先核对远端变化，安全合并，不强推覆盖他人修改。
3. 核对最终候选源码和提交一致。创建对应提交的新 tag，确认远端 tag 指向正确提交，再调用 `gh release create --verify-tag`，不让 GitHub 自动从错误的分支头创建 tag。
4. 稳定正式版本才标为 Latest。现有入口只支持 `X.Y.Z`，不擅自增加 rc / beta 版本体系；已有 tag、Release 和附件默认保留。
5. 从已验证报告形成明确的运行包上传清单，按 `RELEASE.md` 核对名称、版本、大小与 SHA-256。只上传本轮选定平台，不使用可能混入旧版本或 `-validation.zip` 的宽泛通配符。日志、二维码、真实音频、凭据和调试材料不上传，Linux 不发布空壳包。
6. 发布说明写用户可感知的最终变化，通常 3–5 点，加安装要求和必要限制，校验值可折叠。宿主名称统一为 `MyGo Music`；不粘贴内部迭代流水账。
7. 歌手名或其他以 `@` 开头的文本改写或用代码格式；只有确实需要通知真实 GitHub 用户时才使用用户名提及。
8. 发布后核对公开版本、选定平台附件名称、大小及 SHA-256。使用现有 `test/host_release_test.go` 的 `TestQishuiPublishedRelease`，配合现有 overlay 和该测试声明的 `QISHUI_CHECK_RELEASE` / 版本 / 前版本 / SHA-256 环境变量，完成一次匿名版本发现、平台选择、下载哈希及新目录安装验证，不覆盖用户已安装插件。
9. 记录未发布、已发布待核验、已发布核验失败或已发布核验通过的实际阶段。上传或核验失败先检查远端现状，不能盲目重建 Release、移动 tag、覆盖附件或删除线上内容。

## 6. 文案与仓库元数据任务

- 更新发布说明前读取现有正文，只改用户指定内容，不顺便改附件、tag、版本或其他字段；修改后核对结果。
- 更新项目介绍 / Topics 前读取现状，只修改授权字段。默认保留原有 Topics，只有明确“只保留 / 替换全部”才删除其他标签；修改后核对集合。
- 本项目约定的 Topics 为 `mygo-music-plugin`、`qishui-music`、`soda-music`；每次仍须读取实际现状，不把这份列表当成静默重置指令。`mygo-music-plugin` 用于插件发现，未经明确要求不移除。
- 中英文 README 变更按文档任务验证，不因此改插件版本或重发安装包。给草稿或预览不等于授权发布文案。

## 7. 清理与回滚

清理必须由用户明确发起，不作为发布的默认步骤。先盘点路径、大小、当前候选与证据引用，读取仍使用旧解压目录的构建脚本及配置。只删除已授权的旧生成产物，保留当前交付、必要日志 / 报告和固定构建输入；删除前检查实际目标，避免越过目录边界或跟随链接误删。清理后核对保留包与组件哈希，报告实际释放空间。

不通过清理旧包来推进发布，不顺便删除仓库外内容、用户文件、账号数据或 GitHub 附件。回滚指导重新导入旧版本对应架构包，或按授权撤销源码提交；不会撤销已经成功写入汽水账号的操作，不自动删除线上 Release。
